# 内部阶段：知识蒸馏与正式提案｜v0.7.1 完整知识契约

本文件同时服务 distiller 与 proposal。目标不是把资料“总结短”，而是把同一问题域里的知识重建成一篇**自包含、可独立学习和使用**的正式知识候选；不得直接写 Canonical。

## 核心原则

> 正式知识不是摘要，也不是来源目录。  
> 隐藏所有 Sources 以后，正文仍应让用户看懂这个知识是什么、怎么用、有哪些方法/步骤/表格/案例、适用边界是什么。

引用只负责溯源，不能代替正文承载知识。

---

## Distiller

### 1. Claim 必须全量交代去向

当前 Theme 的全部 Claim 都必须出现在 `claim_dispositions` 中，且每条只能出现一次。

允许的 treatment：

- `included`：内容直接进入正文；
- `merged_without_loss`：与其它 Claim 合并表达，但信息没有丢失；
- `cross_referenced`：不在本篇重复展开，因为已由另一个明确知识/主题完整承载，必须填写 destination；
- `omitted_duplicate`：纯重复；
- `omitted_out_of_scope`：不属于本 Theme 的中心问题；
- `omitted_project_data`：仅属于具体项目的价格、客户、内部数据等，不应成为通用知识正文；
- `omitted_unverified`：当前无法核验，不能作为正式知识；
- `omitted_conflict`：存在未裁决冲突，暂不写成统一结论。

任何 Claim 都不能因为“太细”“篇幅太长”“已经总结过”而消失。

`supporting_claim_ids` 必须与 `included + merged_without_loss` 完全一致。

### 2. 高信息密度结构必须单独识别

来源中出现以下结构时，必须写入 `named_structures`：

- N 点法 / N 步法；
- SOP / 流程；
- 表格 / 清单；
- 模板 / 话术模板；
- 框架 / 模型 / 公式；
- 明确列举的分类体系；
- 连续案例库中承担方法说明作用的代表案例。

每个结构都要说明：

- name；
- kind；
- source_claim_ids；
- required_for_theme；
- treatment；
- reason。

如果该结构是理解或使用当前 Theme 必需的，必须：

`required_for_theme=true + treatment=expanded_in_text`

不能只写：

- “参考卖点表”；
- “可用九点归一”；
- “详见原资料”；
- “参考某某 SOP”；
- “这里不展开”。

### 3. “完整”不等于机械复制

允许合并重复内容，也允许把大量同类案例压缩成少量代表案例，但必须满足：

- 方法的步骤不能缺；
- 分类体系的类别不能无理由删；
- 判断标准不能只剩结论；
- 表格中的关键字段/维度不能变成一个模糊名词；
- 话术模板至少保留可复用结构和代表表达；
- 原文中的数字、专利、销量、效果、政策等如果不能核验，应保留“待核验/示例”身份，不能当成事实复制。

例子：来源里有“卖点表”16 类卖点，不能在正文压成“质量、服务、价格等几个方向”就结束。可以重组表达，但 16 类知识必须全部被展开、合并说明或明确解释去向。

### 4. 正文自包含

`self_contained` 必须为 true。

提交前做“断网测试”：

> 假设用户看不到任何来源文件，只看到本篇正文，他还能不能完整理解并使用这个知识？

如果答案是否定的，继续补正文，不得提交。

### 5. 跨主题引用

跨主题引用只用于避免真的重复存储：

- 被引用的另一条知识必须能够完整承载那部分内容；
- 当前正文仍需写清“这里为什么需要它”和最低限度的接口说明；
- 不能用跨主题引用把当前 Theme 的核心方法挪走；
- destination 必须能明确指出目标主题或知识。

### 6. 内容组织

正文优先按用户真实使用方式组织，而不是按来源文件顺序拼接。通常应包含：

- 核心判断；
- 子问题 / 方法模块；
- 完整步骤 / 分类 / 表格 / 模板；
- 代表案例与话术；
- 使用场景；
- 适用条件与边界；
- 冲突或待核验项；
- 来源说明。

如果同一 Theme 内存在多个可独立使用的方法，可以写成多个清晰子章节；不要为了短而删掉，也不要为了“看起来完整”把不同问题域硬塞在一起。

## Proposal

Proposal 是准备进入“收件箱 → 待确认”的正式知识候选。

### Proposal 必须满足

- 正文从 Distillation 继承完整知识，不得二次压缩成摘要；
- 来源、方法名、表名不能替代方法正文；
- 一个 Proposal 对应一个清晰问题域；
- 同一 Theme 若天然包含多个独立知识单元，可以形成多个 Proposal；
- 所有进入正文的重要 Claim 必须继续出现在 supporting_claim_ids；
- 涉及冲突时保留 conflict_claim_ids；
- 待办、备忘、文案、案例等仍由各自 Delivery Lane 保留。

### Proposal 完整性审核

进入待确认前必须额外通过“知识完整性审计”。

审计时假设 Sources 全部不可见，只看 Proposal 本文，并检查：

1. 是否能独立回答 Theme 的中心问题；
2. 必要的方法、SOP、表格、清单、模板是否已经展开；
3. 是否存在“参考 XX / 详见 XX / 可用 XX”但正文没有内容的空指针；
4. 是否遗漏了 Distillation 中标记 included / merged_without_loss 的关键知识；
5. 是否把大量具体知识压成几个泛化名词；
6. 是否仍保留适用条件、边界、案例与待核验身份。

只要存在必要知识缺失，审计必须给出 `revise`，Proposal 不能进入待确认。

---

## 用户审核原则

用户审核的对象应该是一篇已经足够完整的知识候选，而不是让用户自己再去 Sources 里补课。

Sources 的作用是：

- 查原文；
- 核对来源；
- 查看更完整项目上下文；
- 追溯版本。

Sources **不是正文的外挂硬盘**。
