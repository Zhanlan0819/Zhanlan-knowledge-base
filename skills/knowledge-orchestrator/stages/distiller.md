# 内部阶段：知识蒸馏与正式提案｜v0.7

本文件同时服务 distiller 与 proposal。目标是把主题级知识形成用户可直接使用的结论，再形成待确认 Proposal；不得直接写 Canonical。

## Distiller

- 每个 Theme 至少形成一份蒸馏结果，并回溯 Theme → Family → Claim → RAW。
- 只使用当前 Theme 的 `family_ids` 所覆盖的支持 Claim；其中既可以包含主 Family，也可以包含跨主题次级引用。
- 跨主题引用只提供当前问题所需的那部分解释，不要把另一个 Theme 的完整正文复制过来。
- 蒸馏结果要保留条件、边界、适用场景和重要例外，不能为了简洁把张力抹平。
- 结论必须是自然中文、可直接阅读和复用的知识，不要只输出数量、内部 ID 或技术状态。
- 已经确认过的来源边界作为背景约束执行；没有变化时不要每阶段长篇重复。
- 如果同一 Theme 内仍有未裁决冲突，必须在结果里保留冲突，不得伪造统一结论。
- 如果写一份蒸馏结果时仍不得不用两个独立中心问题才能讲清，说明 Theme 过宽，应退回 Theme Builder 拆分，而不是继续硬写。

## Proposal

- Proposal 只表示“建议写入正式知识”的候选，不等于 Canonical。
- 每个 Proposal 必须有支持 Claim；涉及冲突时必须同时保留 conflict_claim_ids。
- 本阶段目标仍只使用 `canonical_knowledge`。待办、备忘、文案、案例等不走 Canonical Proposal，而由各自 Delivery Lane 保留。
- Proposal 生成后必须物化为“收件箱 / 待确认”候选；不得直接写 Canonical。
- 用户只在知识库网页完成最终审核：确认到知识库 / 有疑问并批注 / 移入回收站。
- 聊天中的继续、可以、按推荐，不是知识批准。
- 一个 Proposal 对应一个清晰问题域。不同问题域不要为了减少条数硬合并；同一 Theme 若天然包含多个可独立使用的知识单元，可以形成多个 Proposal。
- 候选正文应包含：核心判断、结构化子问题、代表案例/应用、边界、来源、与旧知识的变化说明。
- 全量来源锚点属于技术详情，不应取代用户可读提案正文。
